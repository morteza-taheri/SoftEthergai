## 4. Capacity and Quota Formula

```kotlin
// ServerListUpdates.kt — one authoritative number, one derivation
internal const val MAX_RETAINED_SERVERS: Int = 500
internal const val RESERVED_CAPACITY_PERCENT: Int = 10

internal fun reservedCapacity(total: Int = MAX_RETAINED_SERVERS): Int {
    if (total <= 0) return 0
    val scaled = total.toLong() * RESERVED_CAPACITY_PERCENT
    return ((scaled + 99) / 100).toInt()      // exact integer ceil
}

internal fun manualServerQuota(total: Int = MAX_RETAINED_SERVERS): Int =
    (total - reservedCapacity(total)).coerceAtLeast(0)
```

`(t·10 + 99) / 100` is exactly `ceil(t·10/100)` for every non-negative `t`, with **no floating
point**: 501 → 51 (not 50), 123 → 13 (not 12), 1 → 1 (not 0).

| Total | Reserved | Max manual |
|---:|---:|---:|
| 100 | 10 | 90 |
| 250 | 25 | 225 |
| 500 | 50 | **450** |
| 501 | 51 | 450 |
| 1000 | 100 | 900 |

Verified by test `E the reserved share follows the configured capacity` and
`E a capacity not divisible by ten rounds the reservation upward`.

## 5. Manual-Server Provenance

**Confirmed from real persisted fields — no heuristic, no migration.**

| Surface | Storage | Written by |
|---|---|---|
| Manual-add form | `manual_server` Room table, unique `(host, port, protocol)` | `ManualServerStore.addDetailed` |
| CSV import | `manual_import` JSON file (atomic temp + rename) | `ManualImportStore.addWithinQuota` |

Both count against the one quota, because both occupy server-list slots. A server is **never**
classified as manual because it is missing from the latest API response, and never from its host name
or IP. `ManualServerEntity` and the Room schema are untouched, so **no migration was required**.

The count used by the gate is `productionManualServerRecordCount()`: `manual_server` rows (enabled or
not — a disabled row is still a record the user created) plus imported rows. A failed read counts as
0, which can only make one call more permissive, never let the total exceed the quota.

## 6. Implementation Changes

**New — `repository/ManualServerAdmission.kt`**
One gate for both surfaces. `admit(requested, write)` runs *count → duplicate lookup → allowance →
write* inside a **process-wide** `Mutex` held in the companion object, so two concurrent additions —
from the same store or from the two different stores — cannot both take the last slot. `requested` is
evaluated inside the critical section because "is this a duplicate?" depends on persisted state.
`write` always runs, even at allowance 0, so edits still work when the quota is full. Also defines
`AddOutcome` (`Stored` / `InvalidInput` / `QuotaReached`).

**New — `repository/ImportOutcome.kt`**
Separates "what was in the text?" (parser) from "what was actually persisted?" (store), so the UI
cannot claim an import that the quota refused. Lives in its own file because
`ConnectionListViewModel.kt` is guarded by a source-shape test that scans for class-level `val`
declarations — a second class in that file was indistinguishable from a ViewModel property to that
scan (this actually failed the suite once; see §9).

**`ServerListUpdates.kt`** — added `RESERVED_CAPACITY_PERCENT`, `reservedCapacity()`,
`manualServerQuota()` next to the existing `MAX_RETAINED_SERVERS`. `capRetainedServers` and the
comparator are **unchanged**.

**`ManualServerStore.kt`** — constructor gains `admission` (defaulted to the shared production
instance, so every existing construction site still compiles). `add()` keeps its `Boolean` signature
(now `addDetailed(...) is Stored`, so all existing tests keep their meaning); new `addDetailed()`
returns the three-way `AddOutcome` with the counts a message needs.

**`ManualImportStore.kt`** — new `addWithinQuota(items, admission)`: partial admission. Existing rows
update, as many new rows as fit are stored, the rest are counted in `quotaRejected`. The raw `add()`
stays as the storage primitive (its file-format tests depend on it) and is no longer called by
production.

**`ConnectionListViewModel.kt`** — `importManualCsv` returns `ImportOutcome` and goes through
`addWithinQuota`; `addManualServer` becomes `suspend` and returns `AddOutcome` (the old Boolean could
not distinguish "invalid" from "full"); both write-through paths now apply `capRetainedServers`, so a
completed write cannot leave the table above the total capacity.

**`SettingsScreen.kt`** — the import summary reports **persisted** counts and appends the localised
quota message. Resource lookups use `LocalResources.current` rather than `LocalContext.current`, which
keeps the new code configuration-aware and avoids adding to the file's existing
`LocalContextGetResourceValueCall` backlog.

**`strings.xml` (en / fa / vi)** — `manual_server_quota_reached`, e.g.
"Manual server limit reached. Manually added servers: 450 of 450. Total server-list capacity: 500."

## 7. Duplicate and Concurrency Behavior

**Duplicates take no slot.** The gate asks for 0 new records when the key already exists, so the write
proceeds at allowance 0 and is reported as `Stored(updated = true)`. This holds at the quota and above
it — which is precisely what keeps an over-cap installation repairable.

**Concurrency.** `ManualServerAdmission.Companion.lock` is shared by every instance, deliberately: both
stores are constructed per call, so an instance-level lock would serialise nothing. Test
`H concurrent additions cannot exceed the quota` fires 40 parallel adds against a quota of 10 and
asserts exactly 10 stored, 30 refused, and a persisted count of 10. Test `H a rejected addition leaves
no partial record` asserts the table is byte-identical after a refusal.

## 8. Total-Cap and Retention Behavior

The two constraints are independent and compose:

- manual ≤ 450 (quota), enforced at the boundary;
- all rows ≤ 500 (capacity), enforced by `capRetainedServers`, which protects every user-supplied row
  and ranks only collected rows.

Because manual is capped at 450 < 500, the manual set can never consume the whole list, and
`capRetainedServers` always has room for at least 50 collected rows. The cap is now applied on the two
ViewModel write-through paths as well, so an import of 450 rows into a 500-row list ends at 500, not
950. Ranking is untouched (quality → breadth → success history → recency → host tie-break), so
`REQ-RETENTION-008` holds.

**Over-cap data** (`REQ-RETENTION-007`): nothing is deleted. `manualCount` reports the real number
(460, not a clamped 450), further additions are refused, and editing/deleting still works.

## 14. Remaining Risks and Open Decisions

| # | Risk | Severity | Evidence / mitigation |
|---|---|---|---|
| R1 | The manual quota counts **all** `manual_server` rows, including disabled ones. A user who disables 100 rows cannot add 100 more. | Low | Deliberate reading of "manual-server records"; documented in §12.8.1. Reversible if the operator prefers "enabled only". |
| R2 | The gate serialises **all** manual writes on one lock. | Very low | Critical section is one indexed count + one insert/file write; no user-observable cost. |
| R3 | An import counts `newRows` from the file, then admits up to the allowance; if the file were mutated between the two reads the counts could skew. | Very low | Both reads happen inside the same critical section; the file is only written by this class. |
| R4 | `addManualServer` changed signature (`Boolean` → `suspend … AddOutcome`). It has **no** production caller today (the form was replaced by CSV import), so nothing broke — but any out-of-tree caller would. | Low | Verified by grep across `app/src`; noted here for the record. |
| R5 | The capacity is a compile-time constant, not a runtime setting. | Informational | Explicitly permitted by the brief ("preserve that architecture"); the quota is still derived, so raising the constant updates both numbers. |
| R6 | Device verification of the at-limit UX is outstanding. | Low | Not achievable without manufacturing records; covered by JVM tests plus a manual-verification recipe below. |

**Open decision for the operator (not invented here):** whether disabled `manual_server` rows should
consume quota (R1). Current behaviour: yes.
